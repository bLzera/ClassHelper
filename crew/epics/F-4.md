# Épico F-4 — Dashboard (listagem)

> **Épico de FRONTEND.** Gate = `run-fe-tests.sh` + `run-fe-lint.sh` (ver F-2). Depende de **F-2** e **F-3**.

## Objetivo

Tela principal do produto: buscar as tarefas do usuário em `GET /dashboard` (já vêm ordenadas por
prioridade efetiva pelo backend) e renderizá-las, com estados de carregamento, vazio e erro.

## Contrato da API consumida

```
GET /dashboard  (Bearer obrigatório)
  200 { assignments: Array<{ id, title, description, due_date, state,
                             manual_priority, auto_priority, course_id }> }
  401 { error: "unauthorized" }

Ordenação: o backend já entrega por COALESCE(manual_priority, auto_priority) ASC NULLS LAST.
           O frontend NÃO reordena — apenas exibe na ordem recebida.
Prioridade efetiva exibida: manual_priority ?? auto_priority (pode ser null → "sem prioridade").
```

## Critérios de aceitação (specs obrigatórios)

1. Ao montar, `DashboardView` chama `GET /dashboard` e renderiza um `AssignmentCard` por item, na
   ordem recebida (sem reordenar no client)
2. Cada card mostra `title`, `due_date` formatada e a prioridade efetiva (`manual_priority ?? auto_priority`);
   quando ambas são `null`, exibe um rótulo de "sem prioridade"
3. Estado de **loading**: enquanto a request não resolve, exibe indicador de carregamento
4. Estado **vazio**: resposta com `assignments: []` exibe mensagem de "nenhuma tarefa"
5. Estado de **erro**: falha na request exibe mensagem de erro (e não quebra a tela)
6. Store `assignments`: `fetchDashboard()` popula a lista e alterna `loading`/`error` corretamente
   (mockar o axios/api)

## Considerações especiais

- **Não reordenar** no client — confiar na ordem do backend (regra de prioridade vive no backend).
- Formatação de data: usar `Intl.DateTimeFormat` (pt-BR) ou similar; tratar `due_date` null.
- Tailwind para o layout; manter componentes pequenos e testáveis.
- A edição de prioridade é o **F-6** — aqui a prioridade é só leitura.
- O botão de sync é o **F-5** — não incluir aqui.
